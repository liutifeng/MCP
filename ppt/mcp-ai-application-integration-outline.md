# 面向 AI 应用集成的 MCP 与网关 PPT 大纲

> 基于文档：`docs/mcp-ai-application-integration-guide.md`  
> 结构定位：先建立 MCP 的基础认知，再讲 MCP Server 的能力设计，最后展开 MCP Gateway 的治理价值。

## 1. 封面

**标题**：面向 AI 应用集成的 MCP 与网关  
**视觉关键词**：能力接入，统一治理  

讲述要点：

- 从 AI 应用集成与治理视角理解 MCP。
- 重点是 AI 应用如何通过 MCP 接入外部系统。
- 建立 MCP Server 与 MCP Gateway 的整体关系。

建议视觉：

- 左侧：AI 应用。
- 中间：MCP / Gateway。
- 右侧：工具、资源、外部系统。

## 2. 目录

页面内容：

1. AI 应用为什么需要 MCP。
2. MCP 的核心角色。
3. MCP Server 怎么设计能力。
4. MCP Gateway 管什么。
5. 落地路径与常见问题。

讲述要点：

- 先讲 MCP 解决什么问题。
- 再讲 Server 如何把外部能力包装给 AI 应用。
- 最后讲 Gateway 如何统一治理这些能力。

建议视觉：

- 用 5 个模块卡片展示全篇结构。
- 强调从“能力接入”走向“统一治理”。

## 3. 背景：AI 应用为什么需要连接外部世界

**核心观点**：大模型只负责推理和生成，真实企业任务必须访问外部系统。

页面内容：

- 读项目文档。
- 查数据库。
- 调内部 API。
- 搜索知识库。
- 查看日志、指标、告警。
- 创建工单、发起审批。

讲述要点：

- 模型本身不知道企业当前数据。
- 企业 AI 应用的价值，往往来自“模型 + 企业上下文 + 外部动作”。
- MCP 要解决的不是模型能力问题，而是外部能力接入问题。

## 4. 痛点：点对点集成会失控

**核心观点**：没有标准协议时，每个 AI 应用都要重复对接外部系统。

页面内容：

```text
Agent A -> 主数据 API / 知识库 API / 日志平台 API
Agent B -> 主数据 API / 知识库 API / 日志平台 API
Agent C -> ...
```

痛点：

- 接入重复。
- 能力不可发现。
- 权限分散。
- 审计困难。
- 风险不可控。
- 工具描述、参数、错误格式不统一。

讲述要点：

- 接入越多，复杂度越高。
- 真正的问题不是“能不能调 API”，而是“能不能标准化、可治理地调 API”。

## 5. MCP 是什么

**核心观点**：MCP 是让 AI 应用以标准方式发现、读取和调用外部能力的协议。

页面内容：

一句话定义：

> MCP 把外部系统包装成 AI 应用可理解、可调用、可治理的标准能力。

MCP 回答的问题：

- 有哪些能力可用？
- 每个能力需要什么参数？
- 哪些内容可以作为上下文？
- 哪些动作可以由模型发起？
- 调用结果如何返回？
- 客户端和服务端如何协商能力？

讲述要点：

- MCP 不是业务系统本身。
- MCP 更像 AI 应用和外部能力之间的标准连接方式。

## 6. MCP 的四个角色

**核心观点**：先理解 Host、Client、Server、Gateway，再看协议细节。

页面内容：

```text
用户 -> MCP Host / AI 应用 -> MCP Client -> MCP Server -> 外部系统
```

角色解释：

- Host：AI 应用本体，管理用户体验、模型调用、权限决策。
- Client：Host 创建的连接会话，负责和某个 Server 通信。
- Server：外部能力适配器，把业务系统包装成 MCP 能力。
- Gateway：企业级统一入口和治理层。

讲述要点：

- MCP Server 可以理解成“能力适配器”。
- Gateway 不是协议必选项，但企业落地时很关键。

## 7. MCP Server 的能力设计

**核心观点**：MCP Server 的关键在于把业务系统能力设计成 AI 可理解、可调用、可治理的接口。

页面内容：

MCP Server 设计要回答：

- 代表哪个业务域？
- 暴露哪些能力给 AI？
- 哪些只是读取上下文？
- 哪些会产生副作用？
- 哪些工具可以自动调用？
- 哪些工具必须人工确认？
- 哪些数据要脱敏？
- 调用过程如何审计？

讲述要点：

- MCP Server 不是简单把 API 原样透出，而是重新组织成适合 AI 使用的能力。
- 能力边界、权限、风险等级，需要应用、平台、安全、业务一起参与。

## 8. 三类核心能力：Tools / Resources / Prompts

**核心观点**：MCP Server 暴露给 AI 应用的能力，主要分成三类。

页面内容：

| 类型 | 怎么理解 | 示例 |
| --- | --- | --- |
| Tools | AI 能做什么 | 查主数据、创建工单、跑查询 |
| Resources | AI 能看什么 | 文件、文档、日志、主数据记录 |
| Prompts | 经验如何模板化 | 代码审查、故障分析、数据治理模板 |

讲述要点：

- Tools 是动作，风险最高。
- Resources 是上下文，关键在权限和准确性。
- Prompts 是团队经验沉淀，不是模型随意调用的工具。

## 9. 从一次调用链理解 MCP

**核心观点**：通过一次工具调用链，理解 MCP 如何把 AI 问答连接到真实业务系统。

用户问题：

> 帮我查询这条主数据记录的状态，并给出处理建议。

调用链：

```text
用户
 -> AI 应用
 -> 大模型判断需要调用查询工具
 -> MCP Client
 -> 数据 MCP Server
 -> 主数据平台
 -> 返回记录详情、字段规则、处理建议
```

讲述要点：

- 模型不是直接访问主数据平台。
- Host 会先看到模型想调用什么能力。
- MCP Server 对接真实系统能力。
- 权限、确认、审计可以放在 Host、Server 或 Gateway 中。

建议视觉：

- 使用时序图。
- 标出 `get_master_data`、`get_field_rules` 两个能力。

## 10. MCP 服务调用示例

**核心观点**：主数据只是示例，重点是 MCP 如何让 AI 应用安全调用企业能力。

业务目标：

> 查询这条主数据记录的状态，说明可用规则，并给出下一步处理建议。

AI 需要的能力：

- 识别工具。
- 网关校验。
- 服务执行。
- 结果治理。

讲述要点：

- AI 应用根据工具名称、参数和描述选择能力。
- Gateway 按用户、角色、租户和策略判断是否允许调用。
- MCP Server 调用主数据平台并整理返回结构。
- 结果返回前可以统一脱敏、审计和观测。

## 11. 为什么需要 MCP Gateway

**核心观点**：MCP Server 解决“怎么接能力”，MCP Gateway 解决“能力多了以后怎么管”。

页面内容：

直连模式问题：

- 每个 Agent 都要配置很多 Server。
- 权限策略散落。
- 工具命名冲突。
- 审计困难。
- 高风险调用难以统一阻断。

网关模式价值：

- 统一入口。
- 统一工具目录。
- 统一权限。
- 统一策略。
- 统一审计。
- 统一路由与观测。

建议视觉：

```text
多个 Agent -> MCP Gateway -> 多个 MCP Server
```

## 12. MCP Gateway 核心职责

**核心观点**：MCP Gateway 是 AI 外部能力的治理入口。

页面内容：

| 职责 | 讲法 |
| --- | --- |
| 服务注册 | 企业内部 MCP 能力目录 |
| 工具目录 | AI 应用可用能力清单 |
| 统一入口 | 降低 Agent 接入复杂度 |
| 权限控制 | 防止越权调用 |
| 策略治理 | 高风险工具确认、阻断、脱敏 |
| 路由转发 | 转到后端 MCP Server |
| 审计日志 | 调用可追溯 |
| 可观测性 | 统计延迟、失败率、调用量 |

讲述要点：

- 网关不一定做业务逻辑。
- 网关重点做治理、路由、策略和可观测。

## 13. MCP Gateway 与 API Gateway、AI Gateway 的区别

**核心观点**：三类网关关注点不同，不是互相替代。

页面内容：

| 类型 | 管什么 | 典型问题 |
| --- | --- | --- |
| API Gateway | 业务 API 流量 | 路由、鉴权、限流、熔断 |
| AI Gateway | 模型调用流量 | 模型路由、成本、token、内容安全 |
| MCP Gateway | 工具和上下文能力 | 工具治理、资源访问、MCP 会话、审计 |

组合关系：

```text
AI 应用 -> AI Gateway -> 模型服务
AI 应用 -> MCP Gateway -> MCP Server -> API Gateway -> 业务系统
```

讲述要点：

- API Gateway 管业务 API。
- AI Gateway 管模型请求。
- MCP Gateway 管 AI 可以使用哪些外部能力。

## 14. 面向 AI 应用集成的设计方法

**核心观点**：不要一上来问怎么写 Server，先问 AI 场景和能力边界。

页面内容：

四步设计法：

1. 识别 AI 场景：用户希望 AI 完成什么任务？
2. 区分上下文和动作：AI 需要看什么，做什么？
3. 按风险给工具分级：只读、敏感只读、低风险写、高风险动作。
4. 决定网关策略：工具目录、权限、审计、审批、多租户。

能力示例：

- 需要看：业务记录、系统文档、日志指标、规则说明。
- 需要做：创建工单、生成报告、提交审批。
- 高风险：合并、删除、强制生效、改权限。

## 15. 企业落地风险

**核心观点**：MCP 的风险来自“模型可以使用外部能力”。

页面内容：

重点风险：

- Prompt Injection：外部内容诱导模型调用敏感工具。
- 资源越权读取：读取不该看的主数据或日志。
- 工具组合风险：多个低风险工具组合后造成泄露。
- 影子 MCP Server：未经审核的服务被接入。

控制建议：

- Host 和 Gateway 不能只相信模型判断。
- Resource 读取绑定用户身份。
- 高风险工具必须确认或审批。
- 敏感数据脱敏。
- MCP Server 注册审核和白名单。

## 16. 落地路线

**核心观点**：从只读场景开始，逐步引入写操作和网关治理。

页面内容：

```text
阶段 1：只读资源接入
知识库、文档、FAQ、项目 README

阶段 2：低风险查询工具
查主数据状态、查日志、查指标

阶段 3：受控写操作
创建工单、生成报告、发起草稿

阶段 4：高风险动作治理
合并、删除、发布、权限变更

阶段 5：MCP Gateway 平台化
服务注册、工具目录、鉴权、策略、审计和观测
```

讲述要点：

- 不建议一开始就开放高风险工具。
- 先把可读上下文和低风险查询做稳。
- 网关能力随着 MCP Server 数量和风险等级逐步增强。

## 17. 总结页

**核心观点**：MCP 解决接入，Gateway 解决治理。

页面内容：

```text
MCP 解决：AI 应用如何标准化连接外部能力。
MCP Server 解决：把业务系统包装成 AI 可理解、可调用的能力适配器。
Tools 解决：AI 能做什么。
Resources 解决：AI 能看什么。
Prompts 解决：团队经验如何模板化复用。
MCP Gateway 解决：能力多了以后如何统一入口、权限、策略、审计和治理。
```

收束句：

> MCP 是 AI 应用接入外部世界的协议，MCP 网关是企业治理这些外部能力的入口。

## 18. Q&A 备选页

可准备的问题：

- MCP 会替代 API 吗？
- 有了 API Gateway，还需要 MCP Gateway 吗？
- 模型能不能直接调业务 API？
- MCP Server 是不是越多越好？
- 应用、平台和业务团队如何参与 MCP 建设？

建议回答方向：

- MCP 不替代业务 API，而是在 AI 应用和业务 API 之间增加面向模型的能力适配。
- MCP Gateway 和 API Gateway 管的对象不同。
- 直接让模型调 API 在生产环境风险较高。
- MCP Server 要按能力域设计，不是越多越好。
- 应用、平台和业务团队可以参与场景梳理、能力边界、风险分级、权限与治理策略设计。
