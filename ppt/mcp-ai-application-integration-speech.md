# MCP 服务与 MCP 网关技术分享演讲稿

> 建议时长：30-40 分钟  

## 01 / 封面

大家好，今天我分享的主题是“MCP 服务与 MCP 网关技术”。

这次我将从企业 AI 应用集成的角度聊 MCP。我们会看三个问题：AI 应用为什么需要 MCP，MCP服务 在里面承担什么角色，以及当 服务 越来越多之后，为什么还需要 MCP 网关来做统一治理。

MCP 的价值不止是让模型“能调工具”。更关键的是，它把外部系统能力整理成一套标准连接方式，让 AI 应用能够发现、调用，也方便后续治理。

转场：我们先从最基本的问题开始，为什么 AI 应用会需要连接外部世界。

## 03 / 背景：AI 应用为什么需要连接外部世界

大家应该对大模型也有一定的了解，大模型主要擅长推理、生成、总结和规划，但企业里的真实任务，往往还要依赖模型之外的信息和动作。

比如用户可能希望 AI 帮他读项目文档、查数据库、调用内部 API，甚至创建工单、发起审批等等。

这些事情有一个共同点：它们都依赖企业当前的数据、当前的系统状态，以及真实业务系统里的动作能力。

企业 AI 应用的价值，往往来自“模型 + 企业上下文 + 外部动作”。模型只是其中一部分。AI 能不能落到业务里，关键看它能不能安全、稳定、标准化地连接企业系统。

这就是 MCP 出现的背景。模型已经越来越会推理了，接下来更现实的问题是：模型和外部能力之间，怎么连接才可靠、可控。

## 04 / 痛点：点对点集成会失控

在没有统一协议和治理方式的时候，每个 AI 应用都要重复对接外部系统。

比如 Agent A 要接主数据 API、知识库 API、日志平台 API；Agent B 也要接同样的一批系统；后面再来 Agent C、Agent D，大家都重复造一遍连接逻辑。

一开始这看起来只是多写几个接口，但规模起来以后问题会很明显。

第一，接入重复。每个应用都在做相似的适配工作。

第二，能力不可发现。企业里到底有哪些能力可以给 AI 用，很难形成统一目录。

第三，权限分散。每个应用自己管权限，很容易出现策略不一致。

第四，审计困难。谁调用了什么工具、访问了什么数据、产生了什么结果，不容易统一追踪。

第五，风险不可控。尤其是高风险操作，如果散落在各个 Agent 里，很难统一阻断或确认。

第六，工具描述、参数和错误格式不统一。模型看到的能力说明不一致，就会影响调用准确性和稳定性。

问题的关键从“能不能调 API”，变成了“能不能用标准化、可治理的方式调 API”。

转场：MCP 就是围绕这个问题给出的标准化连接方式。

## 05 / 由来：MCP 不是某个产品，而是一套开放规范

当大模型应用只做问答、总结和生成时，大家主要关注模型能力本身。可是一旦 AI 要读文档、查数据库、调用企业 API，一串工程问题就冒出来了：这些能力怎么暴露给 AI 应用？怎么描述？怎么传参？怎么返回结果？权限和审计放在哪里做？

如果每个 Agent 都自己定义一套工具格式、上下文格式和错误格式，短期可以跑起来，长期会非常难治理。

MCP 就是在这个背景下出现的。它不负责替代业务系统，也不是某个单独产品；更准确地说，它是一套开放规范。它最初由 Anthropic 在 2024 年 11 月开源发布，目标是给 AI 应用连接外部工具、数据源和上下文提供统一协议。Anthropic 也是 Claude 背后的公司，本身就在做面向大模型应用的产品和研究。

还有一点要提前说明：MCP 规范会继续演进。它有明确的协议版本，官方文档和规范也会随着实现经验、社区提案和兼容性要求更新。企业落地时，一方面要理解当前协议定义了什么，另一方面也要关注版本兼容和治理边界。

大家可以先把它看成 AI 应用访问外部能力的连接标准：它定义怎么连接、怎么描述能力、怎么交换上下文；后面的业务 API、数据库和企业系统依旧各自承担原来的业务职责。

转场：有了这个背景之后，我们再看 MCP 到底标准化了什么。

## 06 / 定义：MCP 是什么

MCP 的全称是 模型上下文协议。

简单说，MCP 定义的是 AI 应用与外部能力之间的通信方式。
可以抓住三个关键词。

第一个是“可理解”。AI 应用和模型要知道有哪些能力、这些能力是什么意思、调用时需要什么参数。

第二个是“可调用”。能力不能只停留在文字说明上，还要能通过标准协议发起真实调用。

第三个是“可治理”。MCP 协议本身不会自动完成所有治理，但当能力、参数、上下文和调用结果被标准化之后，Host、Server 和后面的 Gateway 才有条件做权限控制、风险分级、审计记录和策略约束。

MCP 主要回答六类问题：有哪些能力可用；每个能力需要什么参数；哪些内容可以作为上下文；哪些动作可以由模型发起；调用结果如何返回；客户端和服务端如何协商能力。

从这个角度看，MCP 更像 AI 应用和外部能力之间的一层标准通信方式。业务系统还是业务系统，业务 API 也还在后面提供真实能力。

## 07 / 角色：Host、Client、Server 是 MCP 的三段分工

MCP 里有三个核心角色：Host、Client、Server。

Host 就是 AI 应用本体。比如 AI 助手、IDE、智能客服、数据分析助手，都可以是 Host。它负责用户体验、模型调用、权限决策和上下文组织。

Client 是 Host 创建出来的连接会话。通常一条 Client 连接一个 MCP Server，负责按照 MCP 协议和服务端通信。

Server 是外部能力适配器。它把 API、数据库、文档、工具或者其他业务系统能力，包装成 MCP 标准能力暴露给 AI 应用。

我看下这个图，模型不会直接乱调业务系统，正常链路是 Host 组织用户请求和上下文，Client 通过协议连接 Server，Server 再去对接真实外部系统。
【只有MCP Client与MCP Server是双向箭头是为了突出 MCP 协议核心发生在 Client 和 Server 之间】

这样一来，外部能力就有了标准化的呈现方式。模型看到的是经过设计的工具、资源和提示模板，而不是一堆杂乱的内部 API。

转场：理解角色之后，我们看 MCP Server 应该怎么设计。

## 08 / 设计：MCP Server 不是把 API 原样透出

这里有个很关键点：做 MCP Server，不能简单地把 API 原样透出去。

很多人第一次接触 MCP Server，会觉得它就是把已有接口包一层，让模型能调用。企业落地时如果只做到这一步，风险会比较高，效果也不稳定。

更重要的是能力设计。我们要把业务系统能力重新组织成 AI 可理解、可调用、可治理的接口。

设计 MCP Server 时，需要考虑几个问题。

它代表哪个业务域？比如主数据、知识库、日志平台、项目管理。最好按能力域组织，不要什么都混在一起。

它暴露哪些能力给 AI？内部 API 很多，但适合开放给 AI 的只是一部分。

哪些只是读取上下文？哪些会产生副作用？读数据和改数据的风险完全不同。

哪些工具可以自动调用？哪些工具必须人工确认？比如查询状态可以自动执行，但合并、删除、发布、权限变更等就需要更严格的确认。

哪些数据要脱敏？调用过程如何审计？这些问题如果不在 Server 设计阶段想清楚，后面接入越多越难治理。

因此，MCP Server 的价值不只是“接通”。更重要的是给业务能力划出适合 AI 使用的边界。

转场：这些能力在 MCP Server 里通常会分成三类。

## 09 / 能力：Tools / Resources / Prompts

Tools、Resources 和 Prompts。

Tools 对应的是 AI 能做什么。它们通常是动作，比如查询数据、创建工单。Tools 的风险最高，因为它们可能产生真实业务影响。

Resources 对应的是 AI 能看什么，比如文件、文档、日志、数据记录。Resources 的重点是权限和准确性，AI 不能随便读取用户无权访问的内容。

Prompts 对应的是经验如何模板化，比如代码审查模板、故障分析模板、数据治理模板。它的作用是把团队经验沉淀成可复用的提示结构，帮助模型按统一套路处理问题。

这三类能力组合起来，才构成一个比较完整的 AI 外部能力体系：能看、能做，还能按照组织经验做。

## 13 / 调用链：从一次调用链理解 MCP

这里还是用刚刚那个场景来理解。

用户提出问题：查询订单的状态，并给出处理建议。

AI 应用收到问题后，会先把用户问题和可用工具列表交给大模型，而不是直接访问内部工单平台。

大模型根据工具描述判断：这个问题可能需要调用 get_order_status 和 search_tickets 这类工具。

发起调用之前，AI 应用或网关可以先检查用户权限和工具风险。比如这个用户有没有权限查看这笔订单和相关工单，调用这些工具是否属于敏感查询。

确认可以调用后，AI 应用通过 MCP Client 发起请求。MCP Client 把请求转成 MCP 标准请求，发送给工单 MCP Server。

MCP Server 再去查询内部工单平台，获取订单状态、关联工单列表类工单详情。

内部工单平台返回详情后，MCP Server 会整理成 MCP 标准响应，再返回给 MCP Client。 MCP Client给AI 应用返回工具结果。

AI 应用拿到工具结果后，再连同用户问题一起交给大模型，由模型生成最终解释，以及下一步处理建议是什么。

这条链路说明MCP 的目的不是让模型绕过应用直接访问数据库。它是让外部能力通过标准协议、有边界地进入 AI 应用。

转场：再进一步看，企业能力调用时还需要哪些安全控制。

## 14 / 示例：让 AI 应用安全调用企业能力

这里我们要看的重点，是 MCP 如何帮助 AI 应用安全调用企业能力。

整个调用过程可以拆成四步。

第一步是识别工具。AI 应用根据工具名称、参数和描述，让模型判断应该选择哪个能力。比如查询订单状态可以用 get_order_status，搜索相关工单可以用 search_tickets。

第二步是网关校验。网关可以按照用户、角色、租户和策略判断是否允许调用。比如同一笔订单或同一个工单，不同部门、不同角色的可见范围可能不一样。

第三步是服务执行。工单 MCP Server 调用内部工单平台，并把订单状态、关联工单和工单详情整理成适合 AI 使用的结构。

第四步是结果治理。结果返回前可以统一做脱敏、审计和观测。比如隐藏敏感字段，记录调用链路，统计失败率和延迟。

从这里能看出来，MCP服务和网关的职责是互补的。服务偏能力适配，网关偏统一治理。两者配合起来，AI 调用企业能力才会既好用又可控。

转场：当 MCP服务变多以后，网关的价值会越来越明显。

## 15 / 网关：Server 解决怎么接，Gateway 解决怎么管

这一页的核心观点是：Server 负责把能力接进来，Gateway 负责在能力变多以后把它们管起来。

如果没有 Gateway，每个 Agent 都要配置很多 Server。短期可以跑起来，长期就会出现很多问题。

权限策略会散落在各个应用和 服务里。工具命名可能冲突，比如不同团队都叫 query_user，但含义和权限完全不一样。审计也会很困难，因为调用日志分散在不同系统里。

更麻烦的是高风险调用难以统一阻断。比如删除、发布、权限变更，这类动作如果没有统一治理入口，就很难形成企业级安全策略。

MCP 网关的价值，就在于把这些分散的问题收拢到一个治理入口里处理。

它提供统一入口，让 AI 应用不用逐个接很多 Server。

它提供统一工具目录，让能力可发现、可管理。

它统一权限、统一策略、统一审计，也可以做统一路由和观测。

简单概括就是：MCP Server 解决能力适配，MCP Gateway 解决能力治理。

转场：具体来说，Gateway 应该承担哪些职责呢？

## 16 / 职责：MCP Gateway 是 AI 外部能力的治理入口

MCP Gateway 不一定承担业务逻辑，它的重点放在治理、路由、策略和可观测上。

第一，服务注册。企业内部有哪些 MCP Server、哪些能力可以接入，需要形成能力目录。

第二，工具目录。AI 应用可用能力清单要统一管理，避免每个应用自己维护一套。

第三，统一入口。Agent 接入时不用配置一堆 Server，统一通过 Gateway 访问受管能力。

第四，权限控制。Gateway 可以统一判断用户是否有权限调用某个工具、读取某个资源。

第五，策略治理。比如高风险工具需要确认、阻断或脱敏，都可以在 Gateway 层统一处理。

第六，路由转发。Gateway 根据工具和服务注册信息，把请求转到后端 MCP Server。

第七，审计日志。谁在什么时间调用了什么工具、结果如何，都要可追溯。

第八，可观测性。调用量、延迟、失败率这些指标，对平台化运营都很重要。

从这个角度看，MCP Gateway 更像 AI 外部能力的治理入口，不能只把它看成一个简单转发代理。

转场：那么它和我们熟悉的 API Gateway、AI Gateway 又有什么区别？

## 17 / 边界：MCP Gateway 与 API Gateway、AI Gateway

这三个概念很容易放在一起讨论。

API Gateway 管的是业务 API 流量。它关注路由、鉴权、限流、熔断等问题。

AI Gateway 管的是模型调用流量。它关注模型路由、成本、token、内容安全等问题。

MCP Gateway 管的是工具和上下文能力。它关注工具治理、资源访问、MCP 会话和审计。

它们关注的对象不同，更多是配合关系。

在一条完整链路里，AI 应用调用模型时，可能经过 AI Gateway 到模型服务。

而 AI 应用调用外部工具和资源时，可能经过 MCP Gateway 到 MCP Server，再通过 API Gateway 访问业务系统。

换个说法，API Gateway 更靠近业务 API，AI Gateway 更靠近模型服务，MCP Gateway 更靠近 AI 可使用的外部能力。

转场：到这里，我们可以把前面的关系收拢成一张图。

## 18 / 小结：从能力接入到统一治理

这张图可以从左侧三句话开始看，它把前面的内容收束成三个层次。

接入侧，MCP 服务 把外部系统包装成 AI 可理解的能力。它负责把业务系统的 API、数据、文档和工具，组织成模型能看懂、能调用的标准能力。

治理侧，MCP 网关统一目录、权限、策略、路由和观测。它解决的是能力多了以后怎么管的问题。

边界侧，API 网关管业务 API，AI 网关管模型流量，MCP 网关管工具和上下文能力。三者可以配合，各自守住自己的边界。

右侧结构图可以这样看：AI 应用通过 MCP 进入标准能力连接层，网关负责把工具、资源和外部系统能力统一纳入治理。这样 AI 应用看到的就不再是零散系统，而是一组经过目录化、授权和审计的企业能力。

转场：理解完架构之后，我们来看一下企业落地。

## 19 / 方法：不要一上来问怎么写 Server

很多团队一开始会问：MCP Server 怎么写？用什么 SDK？接口怎么封装？

这些问题当然重要，但一上来就钻到 SDK 和接口里，容易把方向带偏。

第一步应该是识别 AI 场景。前面也提到过，用户到底希望 AI 完成什么任务？是查询信息、分析问题、生成报告，还是发起业务动作？

第二步是区分上下文和动作。AI 需要看什么，做什么？看文档、看日志、看数据，属于上下文；创建工单、提交审批、修改记录，属于动作。

第三步是按风险给工具分级。只读、敏感只读、低风险写、高风险动作，应该有不同的权限和确认策略。

第四步是决定网关策略。包括工具目录、权限、审计、审批、多租户等。

MCP 落地不能只当成一次技术接入。场景、能力边界、风险等级和治理策略，最好一开始就放在一起设计。

转场：为什么要强调风险？因为 MCP 的风险来自模型可以使用外部能力。

## 20 / 风险：风险来自“模型可以使用外部能力”

MCP 的价值，是让 AI 能接触真实系统；它的风险，也正好来自这里。

第一类风险是 Prompt Injection（也就是提示词注入）。外部内容可能诱导模型调用敏感工具，或者绕过原本的指令边界。

第二类风险是资源越权读取。AI 读取资源时，必须绑定真实用户身份，不能因为模型需要上下文就越权读取数据。

第三类风险是工具组合风险。单个工具看起来风险不高，但多个低风险工具组合起来，可能造成敏感信息泄露或业务影响。

第四类风险是影子 MCP Server。未经审核的 Server 被接入，可能带来安全、合规和数据泄露问题。

对应的控制建议也比较明确。

Host 和 Gateway 不能只相信模型判断。模型建议调用某个工具，不代表一定允许执行。

Resource 读取要绑定用户身份。用户看不到的数据，AI 也不能看。

高风险工具必须确认或审批。比如删除、发布、合并、权限变更，不能让模型自动执行到底。

敏感数据要脱敏。MCP Server 注册也要有审核和白名单机制。

转场：那企业应该怎么一步步落地？看下一页路线。

## 21 / 路线：从只读开始，逐步引入写操作和网关治理

企业落地 MCP，不建议一开始就开放高风险工具。更稳妥的方式是分阶段推进。

第一阶段是只读资源接入。比如知识库、文档、FAQ（常见问题）、项目 README。这类场景风险相对低，适合先验证价值。

第二阶段是低风险查询工具。比如查数据状态、查日志、查指标。这个阶段开始引入工具调用，但仍然以查询为主。

第三阶段是受控写操作。比如创建工单、生成报告、发起草稿。这些动作可以产生业务对象，但一般可以设计成低风险、可回滚或需人工确认。

第四阶段是高风险动作治理。比如合并、删除、发布、权限变更。这类能力必须配合审批、确认、审计和更严格的权限策略。

第五阶段是 Gateway 平台化。当 MCP Server 数量变多、风险等级变复杂，就需要服务注册、工具目录、鉴权、策略、审计和观测能力平台化。

这条路线的原则是：先把可读上下文和低风险查询做稳，再逐步引入写操作和统一治理。

转场：最后我们总结一下今天的核心观点。

## 22 / 总结：MCP Server 解决接入，MCP Gateway 解决治理

浓缩成一句话就是：MCP Server 解决接入，MCP Gateway 解决治理。

MCP 协议先定义了 AI 应用和外部能力之间的标准通信方式。

在这个协议基础上，MCP Server 负责把业务系统包装成能力适配器。

能力适配器通常通过 Tools、Resources 和 Prompts 来呈现。

Tools 解决 AI 能做什么。

Resources 解决 AI 能看什么。

Prompts 解决团队经验如何模板化复用。

MCP Gateway 解决能力多了以后如何统一治理。

所以，MCP Server 更偏接入侧，解决“能力怎么接进来”；MCP Gateway 更偏治理侧，解决“能力多了以后怎么管起来”。
