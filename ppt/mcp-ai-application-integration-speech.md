## 01 / 封面

各位好，今天我分享的主题是“MCP 服务与 MCP 网关技术分享”。

这次分享不会只停留在协议名词上，而是从企业 AI 应用集成的角度来看 MCP：为什么 AI 应用需要 MCP，MCP Server 到底承担什么角色，以及当 MCP Server 越来越多以后，为什么还需要 MCP Gateway 做统一治理。

我希望大家听完之后能形成一个比较清晰的判断：MCP 不只是让模型“能调工具”，它更重要的价值，是把外部系统能力变成 AI 应用可以发现、可以调用、可以治理的一套标准连接方式。

转场：我们先从最基本的问题开始，为什么 AI 应用需要连接外部世界。

## 03 / 背景：AI 应用为什么需要连接外部世界

大模型本身擅长的是推理、生成、总结和规划，但企业里的真实任务通常不是只靠模型内部知识就能完成。

比如用户可能希望 AI 帮他读项目文档、查数据库、调用内部 API、搜索知识库、查看日志指标和告警，甚至创建工单、发起审批。

这些事情有一个共同点：它们都依赖企业当前的数据、当前的系统状态，以及真实业务系统里的动作能力。

所以企业 AI 应用的价值，往往来自“模型 + 企业上下文 + 外部动作”。模型只是其中一部分，真正能让 AI 落到业务里的，是它能不能安全、稳定、标准化地连接企业系统。

这也是 MCP 出现的背景：它要解决的不是模型聪不聪明的问题，而是模型和外部能力之间怎么连接的问题。

转场：如果没有标准连接方式，会出现什么问题？我们看下一页。

## 04 / 痛点：点对点集成会失控

在没有统一协议和治理方式的时候，每个 AI 应用都要重复对接外部系统。

比如 Agent A 要接主数据 API、知识库 API、日志平台 API；Agent B 也要接同样的一批系统；后面再来 Agent C、Agent D，大家都重复造一遍连接逻辑。

一开始这看起来只是多写几个接口，但规模起来以后问题会很明显。

第一，接入重复。每个应用都在做相似的适配工作。

第二，能力不可发现。企业里到底有哪些能力可以给 AI 用，很难形成统一目录。

第三，权限分散。每个应用自己管权限，很容易出现策略不一致。

第四，审计困难。谁调用了什么工具、访问了什么数据、产生了什么结果，不容易统一追踪。

第五，风险不可控。尤其是高风险操作，如果散落在各个 Agent 里，很难统一阻断或确认。

第六，工具描述、参数和错误格式不统一。模型看到的能力说明不一致，就会影响调用准确性和稳定性。

所以真正的问题不是“能不能调 API”，而是“能不能标准化、可治理地调 API”。

转场：MCP 就是围绕这个问题给出的标准化连接方式。在正式讲定义之前，我们先把它的由来和规范性质说清楚。

## 05 / 由来：MCP 不是某个产品，而是一套开放规范

MCP 的出现，和 AI 应用接入外部能力的需求直接相关。

当大模型应用只做问答、总结和生成时，问题主要在模型能力本身。但一旦 AI 要读文档、查数据库、调用企业 API、创建工单，问题就变成了：这些能力怎么暴露给 AI 应用？怎么描述？怎么传参？怎么返回结果？怎么做权限和审计？

如果每个 Agent 都自己定义一套工具格式、上下文格式和错误格式，短期可以跑起来，长期会非常难治理。

所以 MCP 不是为了替代业务系统，也不是某个单独产品，而是一套开放规范。它最初由 Anthropic 在 2024 年 11 月开源发布，目标是给 AI 应用连接外部工具、数据源和上下文提供统一协议。

这里还要强调一点：MCP 规范不是一成不变的。它有明确的协议版本，官方文档和规范会随着实现经验、社区提案和兼容性要求继续演进。也就是说，企业落地 MCP 时，既要理解协议当前定义了什么，也要关注版本兼容和治理边界。

可以把它粗略理解成 AI 应用访问外部能力的连接标准：它定义怎么连接、怎么描述能力、怎么交换上下文，但不替代后面的业务 API、数据库和企业系统。

转场：有了这个背景之后，我们再看 MCP 到底标准化了什么。

## 06 / 定义：MCP 是什么

MCP 的全称是 Model Context Protocol，模型上下文协议。

一句话理解，MCP 定义的是 AI 应用与外部能力之间的通信方式：如何发现能力、传递上下文、调用工具并返回结果。

这里有几个关键词。

“可理解”，指的是 AI 应用和模型能知道有哪些能力、这些能力是什么意思、需要什么参数。

“可调用”，指的是这些能力不只是文字说明，而是可以通过标准协议真正发起调用。

“可治理”，不是说 MCP 协议本身自动完成所有治理，而是说它把能力、参数、上下文和调用结果标准化之后，Host、Server 和后面的 Gateway 才有条件做权限控制、风险分级、审计记录和策略约束。

MCP 主要回答六类问题：有哪些能力可用；每个能力需要什么参数；哪些内容可以作为上下文；哪些动作可以由模型发起；调用结果如何返回；客户端和服务端如何协商能力。

所以 MCP 不是业务系统本身，也不是替代业务 API。它更像 AI 应用和外部能力之间的一层标准通信方式。

转场：要理解这层连接方式，就要先理解 MCP 里的核心角色。

## 07 / 角色：Host、Client、Server 是 MCP 的三段分工

MCP 里有三个核心角色：Host、Client、Server。

Host 可以理解成 AI 应用本体。比如一个 AI 助手、IDE、智能客服、数据分析助手，都可以是 Host。它负责用户体验、模型调用、权限决策和上下文组织。

Client 是 Host 创建出来的连接会话。通常一条 Client 连接一个 MCP Server，负责按照 MCP 协议和服务端通信。

Server 是外部能力适配器。它把 API、数据库、文档、工具或者其他业务系统能力，包装成 MCP 标准能力暴露给 AI 应用。

这里有一个容易混淆的点：模型不是直接乱调业务系统。正常链路是 Host 组织用户请求和上下文，Client 通过协议连接 Server，Server 再去对接真实外部系统。

这样一来，外部能力就有了一个标准化的呈现方式。模型看到的不是杂乱的内部 API，而是经过设计的工具、资源和提示模板。

转场：理解角色之后，我们看 MCP Server 应该怎么设计。

## 08 / 设计：MCP Server 不是把 API 原样透出

这一页是一个很关键的观点：MCP Server 不是把 API 原样透出。

很多人第一次理解 MCP Server，会觉得它就是把已有接口包一下，让模型能调用。但企业落地时，这样做风险很高，效果也不稳定。

真正重要的是能力设计。也就是说，要把业务系统能力重新组织成 AI 可理解、可调用、可治理的接口。

设计 MCP Server 时，需要回答几个问题。

它代表哪个业务域？比如主数据、知识库、日志平台、项目管理，最好按能力域组织，而不是随便混在一起。

它暴露哪些能力给 AI？并不是所有内部 API 都适合暴露。

哪些只是读取上下文？哪些会产生副作用？读数据和改数据的风险完全不同。

哪些工具可以自动调用？哪些工具必须人工确认？比如查询状态可以自动执行，但合并、删除、发布、权限变更就需要更严格的确认。

哪些数据要脱敏？调用过程如何审计？这些问题如果不在 Server 设计阶段想清楚，后面接入越多越难治理。

所以 MCP Server 的价值不只是“接通”，而是把业务能力设计成适合 AI 使用的能力边界。

转场：这些能力在 MCP Server 里通常会分成三类。

## 09 / 能力：Tools / Resources / Prompts

MCP Server 暴露给 AI 应用的能力主要有三类：Tools、Resources 和 Prompts。

Tools 可以理解成 AI 能做什么。它们通常对应动作，比如查询主数据、创建工单、跑查询。Tools 的风险最高，因为它们可能产生真实业务影响。

Resources 可以理解成 AI 能看什么。比如文件、文档、日志、主数据记录。Resources 的重点是权限和准确性，AI 不能随便读取用户无权访问的内容。

Prompts 可以理解成经验如何模板化。比如代码审查模板、故障分析模板、数据治理模板。它不是让模型随便发挥，而是把团队经验沉淀成可复用的提示结构。

这三类能力组合起来，才构成一个比较完整的 AI 外部能力体系：能看、能做，还能按照组织经验做。

转场：接下来我们用一次真实调用链，把这些角色和能力串起来。

## 10 / 调用链：从一次调用链理解 MCP

这一页用一个主数据质量场景来理解 MCP 调用链。

用户提出问题：人员主数据质量检核发现重复证件号和必填字段缺失，帮我定位问题。

AI 应用收到问题后，不是直接访问主数据平台。它会先把用户问题和可用工具列表交给大模型。

大模型根据工具描述判断：这个问题可能需要调用 query_master_data 和 query_quality_issues 这类工具。

在真正调用之前，AI 应用或网关可以先检查用户权限和工具风险。比如这个用户有没有权限看这条主数据记录，调用这个工具是否属于敏感查询。

确认可以调用后，AI 应用通过 MCP Client 发起 tools/call 请求。MCP Client 把请求转成 MCP 标准请求，发送给主数据 MCP Server。

MCP Server 再去查询普元 MDM 平台，获取模型数据、质量规则命中情况和问题数据。

MDM 平台返回人员主数据记录、质量检核结果与问题数据后，MCP Server 会整理成 MCP 标准响应，再返回给 MCP Client。

AI 应用拿到工具结果后，再连同用户问题一起交给大模型，由模型生成最终解释：命中的质量规则是什么、问题数据范围在哪里，以及下一步处理建议是什么。

这条链路说明一件事：MCP 不是让模型直接越过应用访问数据库，而是让外部能力通过标准协议、有边界地进入 AI 应用。

转场：再进一步看，企业能力调用时还需要哪些安全控制。

## 11 / 示例：让 AI 应用安全调用企业能力

这里继续用主数据做例子，但重点不是主数据本身，而是 MCP 如何让 AI 应用安全调用企业能力。

整个调用过程可以拆成四步。

第一步是识别工具。AI 应用根据工具名称、参数和描述，让模型判断应该选择哪个能力。

第二步是网关校验。网关可以按照用户、角色、租户和策略判断是否允许调用。比如同一个工具，不同部门、不同角色的可见范围可能不一样。

第三步是服务执行。MCP Server 调用后端主数据平台，并把结果整理成适合 AI 使用的结构。

第四步是结果治理。结果返回前可以统一做脱敏、审计和观测。比如隐藏敏感字段，记录调用链路，统计失败率和延迟。

这说明 MCP Server 和 Gateway 的职责不是互斥的。Server 更偏能力适配，Gateway 更偏统一治理。两者配合，才能让 AI 调用企业能力既好用又可控。

转场：当 MCP Server 变多以后，Gateway 的价值会越来越明显。

## 12 / 网关：Server 解决怎么接，Gateway 解决怎么管

这一页的核心观点是：Server 解决怎么接能力，Gateway 解决能力多了以后怎么管。

如果没有 Gateway，每个 Agent 都要配置很多 Server。短期可以跑起来，长期就会出现很多问题。

权限策略会散落在各个应用和 Server 里。工具命名可能冲突，比如不同团队都叫 query_user，但含义和权限完全不一样。审计也会很困难，因为调用日志分散在不同系统里。

更麻烦的是高风险调用难以统一阻断。比如删除、发布、合并、权限变更，这类动作如果没有统一治理入口，就很难形成企业级安全策略。

MCP Gateway 的价值就是把这些问题集中起来处理。

它提供统一入口，让 AI 应用不用逐个接很多 Server。

它提供统一工具目录，让能力可发现、可管理。

它统一权限、统一策略、统一审计，也可以做统一路由和观测。

所以可以简单理解：MCP Server 解决能力适配，MCP Gateway 解决能力治理。

转场：具体来说，Gateway 应该承担哪些职责？

## 13 / 职责：MCP Gateway 是 AI 外部能力的治理入口

MCP Gateway 不一定要做业务逻辑，它的重点是治理、路由、策略和可观测。

第一是服务注册。企业内部有哪些 MCP Server、哪些能力可以接入，需要形成能力目录。

第二是工具目录。AI 应用可用能力清单要统一管理，避免每个应用自己维护一套。

第三是统一入口。Agent 接入时不需要配置一堆 Server，而是通过 Gateway 访问受管能力。

第四是权限控制。Gateway 可以统一判断用户是否有权限调用某个工具、读取某个资源。

第五是策略治理。比如高风险工具需要确认、阻断或脱敏，都可以在 Gateway 层统一处理。

第六是路由转发。Gateway 根据工具和服务注册信息，把请求转到后端 MCP Server。

第七是审计日志。谁在什么时间调用了什么工具、结果如何，都要可追溯。

第八是可观测性。包括调用量、延迟、失败率等指标，这些对平台化运营很重要。

所以 MCP Gateway 更像 AI 外部能力的治理入口，而不是一个简单转发代理。

转场：它和我们熟悉的 API Gateway、AI Gateway 又有什么区别？

## 14 / 边界：MCP Gateway 与 API Gateway、AI Gateway

这里需要把三个概念区分清楚：API Gateway、AI Gateway 和 MCP Gateway。

API Gateway 管的是业务 API 流量。它关注路由、鉴权、限流、熔断等问题。

AI Gateway 管的是模型调用流量。它关注模型路由、成本、token、内容安全等问题。

MCP Gateway 管的是工具和上下文能力。它关注工具治理、资源访问、MCP 会话和审计。

这三类网关不是互相替代，而是关注对象不同。

在一条完整链路里，AI 应用调用模型时，可能经过 AI Gateway 到模型服务。

而 AI 应用调用外部工具和资源时，可能经过 MCP Gateway 到 MCP Server，再通过 API Gateway 访问业务系统。

所以 API Gateway 更靠近业务 API，AI Gateway 更靠近模型服务，MCP Gateway 更靠近 AI 可使用的外部能力。

## 15 / 小结：从能力接入到统一治理

这一页是阶段小结。

左侧三句话把前面的内容收束起来。

接入侧，MCP Server 把外部系统包装成 AI 可理解的能力。它负责把业务系统的 API、数据、文档和工具，组织成模型能看懂、能调用的标准能力。

治理侧，MCP Gateway 统一目录、权限、策略、路由和观测。它解决的是能力多了以后怎么管的问题。

边界侧，API Gateway 管业务 API，AI Gateway 管模型流量，MCP Gateway 管工具和上下文能力。三者可以配合，而不是互相替代。

右侧结构图可以这样理解：AI 应用通过 MCP 进入标准能力连接层，Gateway 负责把工具、资源和外部系统能力统一纳入治理。这样 AI 应用看到的不是零散系统，而是一组经过目录化、授权和审计的企业能力。

这一页的结论是：MCP 负责让能力能接入，Gateway 负责让能力可治理。

转场：理解完架构之后，企业落地时不要一上来就问怎么写 Server。

## 16 / 方法：不要一上来问怎么写 Server

很多团队一开始会问：MCP Server 怎么写？用什么 SDK？接口怎么封装？

这些问题当然重要，但不是第一步。

第一步应该是识别 AI 场景。用户到底希望 AI 完成什么任务？是查询信息、分析问题、生成报告，还是发起业务动作？

第二步是区分上下文和动作。AI 需要看什么，做什么？看文档、看日志、看主数据，属于上下文；创建工单、提交审批、修改记录，属于动作。

第三步是按风险给工具分级。只读、敏感只读、低风险写、高风险动作，应该有不同的权限和确认策略。

第四步是决定网关策略。包括工具目录、权限、审计、审批、多租户等。

所以 MCP 落地不是单纯的技术接入，而是场景、能力边界、风险等级和治理策略一起设计。

转场：为什么要强调风险？因为 MCP 的风险来自模型可以使用外部能力。

## 17 / 风险：风险来自“模型可以使用外部能力”

MCP 的价值在于让 AI 能接触真实系统，但风险也来自这里。

第一类风险是 Prompt Injection。外部内容可能诱导模型调用敏感工具，或者绕过原本的指令边界。

第二类风险是资源越权读取。AI 读取资源时，必须绑定真实用户身份，不能因为模型需要上下文就越权读取数据。

第三类风险是工具组合风险。单个工具看起来风险不高，但多个低风险工具组合起来，可能造成敏感信息泄露或业务影响。

第四类风险是影子 MCP Server。未经审核的 Server 被接入，可能带来安全、合规和数据泄露问题。

控制建议也很明确。

Host 和 Gateway 不能只相信模型判断。模型建议调用某个工具，不代表一定允许执行。

Resource 读取要绑定用户身份。用户看不到的数据，AI 也不能看。

高风险工具必须确认或审批。比如删除、发布、合并、权限变更，不能让模型自动执行到底。

敏感数据要脱敏。MCP Server 注册也要有审核和白名单机制。

转场：那企业应该怎么一步步落地？看下一页路线。

## 18 / 路线：从只读开始，逐步引入写操作和网关治理

企业落地 MCP，不建议一开始就开放高风险工具。更稳妥的方式是分阶段推进。

第一阶段是只读资源接入。比如知识库、文档、FAQ、项目 README。这类场景风险相对低，适合先验证价值。

第二阶段是低风险查询工具。比如查主数据状态、查日志、查指标。这里开始有工具调用，但主要还是查询。

第三阶段是受控写操作。比如创建工单、生成报告、发起草稿。这些动作可以产生业务对象，但一般可以设计成低风险、可回滚或需人工确认。

第四阶段是高风险动作治理。比如合并、删除、发布、权限变更。这类能力必须配合审批、确认、审计和更严格的权限策略。

第五阶段是 Gateway 平台化。当 MCP Server 数量变多、风险等级变复杂，就需要服务注册、工具目录、鉴权、策略、审计和观测能力平台化。

这条路线的原则是：先把可读上下文和低风险查询做稳，再逐步引入写操作和统一治理。

转场：最后我们用一页总结今天的核心观点。

## 19 / 总结：MCP 解决接入，Gateway 解决治理

今天的核心结论可以浓缩成一句话：MCP 解决接入，Gateway 解决治理。

MCP 解决的是 AI 应用如何标准化连接外部能力。

MCP Server 解决的是把业务系统包装成能力适配器。

Tools 解决 AI 能做什么。

Resources 解决 AI 能看什么。

Prompts 解决团队经验如何模板化复用。

MCP Gateway 解决能力多了以后如何统一治理。

所以 MCP 不是要替代业务系统，也不是要替代 API Gateway。它是在 AI 应用和外部系统之间，增加一层面向模型的能力适配和协议标准。

而 MCP Gateway 则是在企业级落地时，把这些能力统一纳入目录、权限、策略、审计和观测。

最后用一句话收尾：MCP 是 AI 应用接入外部世界的协议，MCP 网关是企业治理这些外部能力的入口。
