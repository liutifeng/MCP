背景

AI 应用必须连接企业的真实世界

大模型负责推理和生成，企业任务的落地依赖当前、准确、受控的外部上下文与动作。

读项目文档规范、接口说明、产品手册、知识库。
查业务数据主数据、数据库、指标、日志、告警。
调用内部 API查询、校验、创建工单、提交审批。
组织业务流程把多个系统能力串成一个可执行任务。
痛点

点对点集成会逐渐失控

问题不只是“能不能调 API”，而是能否标准化、可治理地接入外部能力。

重复对接

Agent A → 主数据 API / 知识库 API / 日志平台 API Agent B → 主数据 API / 知识库 API / 日志平台 API Agent C → ...

治理分散

  • 能力不可发现，工具清单难以统一。
  • 权限、审计、错误处理散落在各处。
  • 工具描述、参数格式、返回结果不一致。
  • 高风险调用缺少统一阻断和确认。
核心定义

MCP 标准化连接外部能力

MCP 把外部系统包装成 AI 应用可理解、可调用、可治理的标准能力。
能力发现 参数描述 上下文读取 工具调用 结果返回 能力协商

调用示例

MCP 服务调用示例

以主数据查询为例，AI 应用通过工具描述识别能力，再由网关完成权限、路由、审计和结果处理。

识别工具模型根据工具名称、参数和描述选择能力。
网关校验按用户、角色、租户和策略判断是否允许调用。
服务执行MCP Server 调用主数据平台并整理返回结构。
结果治理脱敏、审计、观测，并把结果交还给 AI 应用。
网关价值

能力多了以后，治理更关键

MCP Server 解决怎么接能力，MCP Gateway 解决能力多了以后怎么管。

直连模式

  • 每个 Agent 配置多个 Server。
  • 权限策略散落在不同系统。
  • 工具命名和描述容易冲突。
  • 高风险调用难以统一阻断。

网关模式

  • 统一入口和工具目录。
  • 按用户、角色、租户过滤能力。
  • 统一审计、策略和观测。
  • 把请求路由到正确 MCP Server。
网关职责

MCP Gateway 是外部能力治理入口

服务注册企业内部 MCP 能力目录。
工具目录AI 应用可用能力清单。
权限控制防止越权调用。
策略治理确认、阻断、脱敏。
统一入口降低 Agent 接入复杂度。
路由转发转到后端 MCP Server。
审计日志调用过程可追溯。
可观测性延迟、失败率、调用量。

企业风险

风险来自模型可以使用外部能力

协议本身不是风险源，关键是工具、资源、权限和组合行为如何被治理。

Prompt Injection外部内容诱导模型调用敏感工具。
资源越权读取读取不该看的业务数据或日志。
工具组合风险多个低风险工具组合后造成泄露。
影子 MCP Server未经审核的服务被接入。
绑定用户身份 高风险确认 敏感数据脱敏 服务注册审核

问答

可以提前准备的几个问题

围绕协议边界、网关边界和服务规模，常见疑问可以收敛到这几类。

MCP 会替代 API 吗？不会，它是在 AI 应用和业务 API 之间增加面向模型的能力适配。
已有 API Gateway 还需要 MCP Gateway 吗？两者管的对象不同，一个管 API 流量，一个管工具和上下文能力。
模型能不能直接调 API？生产环境风险较高，权限、审计、参数校验会变得分散。
MCP Server 越多越好吗？不是，应该按清晰能力域设计，避免治理成本失控。
